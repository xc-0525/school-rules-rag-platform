摘要

摘　要

针对高校校规制度分散、通知时效性强、事务办理入口零散的问题，本课程设计实现了一个面向在校学生的校园服务智能问答系统。系统以检索增强生成（RAG）与多智能体协作为技术主线，构建&quot;意图理解—检索/工具—证据约束生成—引用校验&quot;的可控问答链路；同时把校园公告、寝室报修、图书馆位置预约、失物招领、文档管理五个业务模块纳入统一门户，并通过 Tool Calling 让问答层直接调用业务数据，实现&quot;问得到&quot;与&quot;办得成&quot;的闭环。 系统后端采用 FastAPI + MySQL + Qdrant + Neo4j 的四层结构，前端采用 Vue 3 + Element Plus，提供流式输出、Agent 轨迹可视化、引用溯源与操作确认等交互能力。测试层面建立 160 项自动化用例，并设计了有/无工具的消融实验：接入校园业务工具后，实时业务问题的工具选对率由 0.125 提升至 1.000，拒答数由 4 降至 0，而面向校规条款的 RAG 对照题命中率保持 1.000 不变，说明工具接入没有削弱原有检索能力。

关键词：检索增强生成；多智能体；工具调用；校园服务；人机交互

一、选题概述

1.1 选题背景

高校学生在校期间高频接触三类信息与事务：一是校纪校规、学籍管理、奖助学金等制度性条款；二是停水停电、考试安排、服务窗口调整等时效性通知；三是报修、预约、失物招领等需提交申请并跟踪进度的事务。当前这三类内容通常分散在学校官网、微信公众号、辅导员群聊与线下服务窗口，存在三个突出问题。

第一，制度文本专业性强、篇幅长。以本校公开制度为例，21 篇制度文件共切分出 504 条可检索条款，学生用关键词在官网检索时很难定位到具体条款，遇到"晚归几次会被处分""奖学金评定条件"这类问题时，往往需要逐篇翻阅。

第二，时效性信息与制度文本混在一起。停水停电通知的有效期可能只有几个小时，如果与长期有效的制度条款混排，既影响阅读也容易造成误判。

第三，事务办理缺少统一入口与进度反馈。学生提交报修后只能反复询问宿管，预约座位需要到现场或使用独立小程序，失物招领信息散落在各个群聊中。

1.2 设计目标

本系统希望用一套统一的门户同时解决"查得到"和"办得成"两个问题，具体目标包括：

1. 面向制度文本提供可溯源的问答：回答必须给出条款依据，无法从资料中得到支撑时应明确拒答，而不是编造。 2. 面向时效信息提供自动过期的公告：公告带生效与失效时间，过期自动从列表与问答中消失。 3. 面向事务办理提供完整闭环：提交、审核、处理、进度查询均在系统内完成。 4. 让问答层能够调用真实业务数据：学生可以直接问"我的报修到哪了""明天图书馆还有位置吗"，系统调用业务接口取实时数据作答。 5. 所有写操作保留人工确认：模型只能生成草稿，最终提交必须由用户在界面上点击确认，避免大模型误操作产生脏数据。

1.3 系统范围与本人工作

系统覆盖智能问答、校园公告、寝室报修、图书馆位置预约、失物招领、文档管理六个功能域，共 60 个后端 Python 模块、23 个前端 Vue/TS 文件。本课程设计由本人独立完成需求分析、交互设计、前后端开发、数据库设计与测试评测量工作。

二、调研背景

2.1 调研情境与目标

本次调研发生在系统立项之前，目的是回答三个问题：学生最常问的制度问题集中在哪些主题；现有信息渠道的痛点具体是什么；同类产品已经解决了哪些环节、还缺什么。调研结论直接用于确定功能优先级，避免"凭感觉做功能"。

2.2 调研对象与方法

调研采用三种方法交叉验证，样本为本校在校学生与一线学生工作人员。

方法对象与规模关注点
问卷调查在校学生 126 份（有效 118 份）高频问题类型、信息获取渠道、等待时长、满意度
半结构化访谈学生 8 人、辅导员 2 人、宿管 1 人具体场景、失败案例、对智能问答的接受度
竞品体验5 款同类产品各完成 3 个典型任务功能覆盖、交互路径长度、回答可信度

问卷结果显示：87% 的受访学生过去一学期至少遇到过一次"找不到具体条款"的情况；遇到制度问题时，61% 首选询问同学或辅导员，只有 19% 会主动翻阅官网制度；对"如果能用一句话问出答案"的接受度为 92%，但其中 74% 明确要求"答案要能指出依据在哪一条"，这直接决定了系统必须做引用溯源，而不能只做一个聊天框。

访谈补充了两个关键细节：一是学生对"AI 乱答"的容忍度很低，宁可不答也不要编造；二是事务类需求（报修、预约）的痛点不在提交，而在"提交后不知道进度"。

2.3 调研结论

将痛点按出现频次与影响程度排序，得到四条结论：

1. 制度问答是最高频需求，且必须可溯源（对应 P0 的引用校验能力）。 2. 通知类信息需要时效管理，过期信息比没有信息更糟（对应 P0 的有效期机制）。 3. 事务办理的核心诉求是进度可见（对应 P1 的状态流转与"我的记录"）。 4. 学生对"对话式办理"有兴趣但顾虑误操作（对应 P1 的草稿确认机制）。

三、市场分析

3.1 同类产品概览

选择 5 款学生实际会接触的产品进行对比，覆盖校园综合服务、学习平台、资讯社区与通用大模型四类形态。

产品形态主要能力与本系统的关系
今日校园校园综合服务 App通知、请假、报修、缴费等事务入口事务覆盖最全，但制度问答缺失
超星学习通学习平台课程、资料、考试、部分图书馆服务学习场景强，校园事务弱
学校官网 + 公众号信息发布制度文件、通知公告信息权威，检索与交互体验差
通用大模型助手对话式 AI开放域问答、文本生成表达流畅，但缺少校内数据、无法溯源、可能编造
知乎 / 百度知道社区问答经验型问答覆盖面广，答案时效与权威性不可控

3.2 对比分析

从"能否回答制度问题""答案是否可溯源""能否办理事务""信息是否时效可控"四个维度对比：

维度今日校园学习通官网/公众号通用大模型本系统
制度问答弱弱仅全文检索强但不稳定强，限定语料
引用溯源无无需人工定位无或伪造条款级引用 + 校验
事务办理强中无无中（四类事务）
时效控制中弱人工维护无生效/失效自动过滤
交互方式表单导航表单导航浏览对话对话 + 表单

对比可见，市场产品在"事务入口"或"开放问答"单点上已经成熟，但缺少把两者结合、且回答可控可溯源的形态。通用大模型的表达能力强，却存在三个致命问题：不知道本校制度、无法给出条款出处、会自信地编造。这恰好是 RAG 与引用校验要解决的。

3.3 差异化定位

本系统的定位是"校园服务门户 + 横切智能层"：底层是五个业务模块提供真实数据，上层是问答 Agent 作为统一入口。学生既可以点菜单办理，也可以直接问；两条路径读写同一套数据，不会出现"页面看不到、问答却答得出来"的不一致。

四、功能需求分析

4.1 用户角色

系统设两类角色。学生可浏览公告、提问、提交报修、预约位置、发布失物信息、预览文档；管理员在此基础上拥有公告发布、文档上传与删除、报修受理、失物审核等管理权限。权限控制贯穿接口层与服务层：接口层用角色判定拦截，服务层再做属主校验，学生访问他人资源统一返回 404，不暴露资源是否存在。

4.2 核心需求分析

结合调研结论与技术可行性，将需求分为三个优先级。

优先级需求说明验收口径
P0制度问答与引用溯源回答必须给出条款依据，无法支撑时拒答拒答准确率、引用通过率可测
P0公告时效管理公告带生效/失效时间，过期自动下架过期公告不出现在列表与问答
P0登录鉴权与权限隔离学生/管理员分权，越权访问被拦截401/403 用例覆盖
P1文档上传与在线预览支持 md/txt/文字版 PDF，扫描件走 OCR上传成功率、预览可用
P1寝室报修闭环提交、受理、完成、进度查询状态机与限流可测
P1图书馆位置预约仅约明天起 7 天，防并发超卖并发抢位只成功一单
P1失物招领先审后发图片上传、管理员审核、状态流转未审内容不进公示栏
P2对话式预约与确认模型生成草稿，用户点确认才落库草稿阶段零写入

4.3 其他需求分析

体验需求。对话类产品最怕"等待无反馈"，因此问答采用 SSE 流式输出，首字延迟控制在可感知范围内；回答下方提供可展开的 Agent 轨迹，让用户看到系统做了什么；所有工具调用与检索结果都以"来源卡片"呈现，用户可自行核对。

安全与合规需求。系统需要处理学号、联系方式等个人信息，设计上采取三条措施：接口全部要求登录，token 使用 HMAC 签名并设置过期；日志只记录工具名、参数与摘要，不落用户原话；失物招领的联系方式需学生自行打码，管理端审核时把关。

可维护性需求。新模块必须按统一约定接入（服务层 + 路由层 + 注册一行），不改动 Agent 核心链路；每个模块同时提供 MySQL 实现与内存实现，保证无数据库环境也能跑通测试。

4.4 非功能指标

指标目标值实测
问答首字延迟≤ 3 s平均 3.2 s（含工具调用）
检索召回 recall@3≥ 0.700.750（双路融合）
自动化测试覆盖核心链路160 项，全部通过
并发预约同一时段仅一人成功8 线程并发恰好 1 成功

五、软件界面设计

5.1 设计原则

界面对应于人机交互课程中的可用性五要素，本系统确定四条原则。

一致性。全站共用一套布局：左侧固定导航、顶部状态栏、内容区卡片化。公告、报修、失物等列表项统一采用"标签 + 标题 + 时间"的头部结构，学生在不同模块间切换时不需要重新学习阅读顺序。

可见性。系统状态始终可见：顶部常驻后端连接状态、向量与图谱模式、当前角色；问答过程中显示"生成中"与节点进度；工具调用结束显示耗时。用户任何时候都知道系统在做什么。

即时反馈与容错。所有提交类操作都有 loading 态与结果提示；危险操作（删除文档、关闭工单、驳回失物）需二次确认；公告横幅可一键关闭且可从公告页恢复，避免误关后无法找回。

渐进披露。首页只呈现对话输入与示例问题，检索依据、Agent 轨迹、耗时统计折叠在答案下方；校园服务的三个模块用页签组织，避免一屏堆满表单。

5.2 信息架构与导航

一级导航五个入口：智能问答、会话历史、校园公告、校园服务、文档管理，另有"关于与状态"用于展示系统运行信息。校园服务内部用页签划分为寝室报修、图书馆预约、失物招领三个子域，各自包含"申请/办理"与"我的记录"两部分，符合"先办事、再看进度"的使用顺序。

5.3 关键界面设计说明

登录与身份。登录页仅保留账号、密码与一句系统定位说明，减少首屏干扰。登录后顶栏用不同颜色的标签区分学生与管理员身份，让权限差异始终可见。

问答主界面。采用经典对话流布局。用户消息右对齐，助手回答左对齐并附带三类辅助信息：来源卡片（可展开查看条款原文）、Agent 轨迹（展示意图理解、检索、生成、校验各节点耗时）、反馈按钮。回答被拒答时，界面明确说明"资料中未提及"，而不是给出模糊答案。

紧急公告横幅。紧急且置顶的公告在登录后悬挂于顶部，红底强调、可一键关闭，关闭记录保存在本地并按公告版本区分；管理员更新公告内容后会重新提示。公告板块本身完整保留，学生可在其中查看全部历史公告。

图书馆预约界面。左侧为位置列表（自习区、研讨间、电子阅览区），右侧为日期选择与三个时段的占用情况，已被预约的时段置灰并标注"已约满"，避免用户点进去才失败。下方"我的预约"表格展示状态与取消入口。

文档管理界面。表格列出标题、文件名、类型、条款数、状态；文件名可点击直接在线预览原件；管理员上传后弹出"本次新增条例"报告，逐条列出新增条款与跳过重复的数量。

5.4 交互细节

对话式办理是本系统的交互亮点：当学生说"帮我预约明天下午的研讨间"时，模型不会直接下单，而是在回答中生成一张"预约草稿"卡片，写明位置、日期、时段，并提供"确认预约"按钮。用户点击后才真正写入预约记录，未确认前不占用任何资源。这一设计同时解决了大模型误操作与学生信任两个问题。

七、系统实现与关键技术

7.1 分层架构

系统分为四层。接入层由 FastAPI 提供 REST 与 SSE 接口，统一鉴权与限流；编排层是 Agent 图，负责意图理解、记忆、检索、工具调用、生成与校验；能力层包含向量检索、图谱检索、业务服务与文档入库；存储层为 MySQL（业务数据）、Qdrant（条款向量）、Neo4j（条款图谱）。

分层的直接收益是模块可替换：向量库从本地嵌入式切换到服务端模式只需改配置，业务模块新增不需要改动 Agent 图。

7.2 Agent 工作流

问答请求进入后依次经过：缓存查询、意图理解（判断是否需要工具、是否涉及实时数据）、多轮记忆、检索或工具调用、证据充分性判定、生成、引用校验、必要时重生成。任一环节失败都有降级路径，例如工具调用异常会回退到标准 RAG，生成结果未通过引用校验会触发一次重生成，仍不通过则拒答。

7.3 检索与融合

制度条款同时进入向量库与图谱。向量检索负责语义相近，图谱检索负责"条款—章节—主题"的关系召回。两路结果经 RRF 融合后进入生成，融合结果带章节、条款号与原文片段，作为引用校验的依据。在 8 道金标题上，双路融合的 recall@3 为 0.750，MRR 为 0.442。

7.4 工具调用与写操作确认

系统向模型暴露 7 个工具：校规检索、公告查询、工单创建，以及报修进度、我的预约、场馆余量、失物检索四个校园服务只读工具，另有一个预约草稿工具。写操作工具只生成 requires_confirmation 草稿，前端根据 action 字段渲染不同的确认按钮，用户点击后才调用真实写接口。

为避免"查询被误判为建单"，系统把"报修""失物"这类名词从建单意图关键词中移除，只保留"我要报修""申请报修"等动作短语，并用提示词明确"查询进度用 query_repair_status，不要 create_ticket"。

7.5 并发控制与数据一致性

图书馆预约是唯一的强并发场景。系统采用两道防线：事务内用 SELECT ... FOR UPDATE 锁住位置行，在锁内检查目标时段是否已被占用；数据库层建立 (location_id, res_date, slot) 唯一索引作为最终兜底。并发冲突统一捕获为 409，前端提示"该时段刚被别人预约"并自动刷新余量。

文档入库的一致性由"先写 MySQL、再写向量与图谱、失败回滚"保证，同时在上传前做条款级去重：以"去掉编号与空白后的正文"为键，同时过滤库中已有条款与文档内重复条款，只写入真正新增的内容，并把新增清单返回给管理员。

八、测试与评测

8.1 测试策略

测试分三层：服务层单元测试覆盖业务规则（限流、判重、状态机、并发），接口层测试覆盖权限与错误码映射，端到端测试用 Playwright 覆盖关键交互路径。当前共 160 项自动化用例，全部通过。

8.2 检索评测

使用 8 道金标题（含 2 道应拒答题）评测检索与生成：recall@3 为 0.750，MRR 为 0.442；端到端拒答准确率与引用通过率均在可接受区间。评测脚本支持 --only 切换融合策略，便于后续做消融对比。

8.3 工具消融实验

为验证"问答接入业务工具"的收益，设计了 8 题的工具评测集，同一批题分别在开启与关闭校园工具时各跑一遍。

配置工具选对率RAG 对照题命中被拒答题数p50 时延
开启校园工具1.0001.00003512 ms
关闭校园工具0.1251.00043245 ms

关闭组 0.125 仅来自 RAG 对照题，说明 7 道实时业务题在无工具时全部拿不到数据；两组 RAG 对照题命中率均为 1.000，说明工具接入没有抢走原有检索调用。实验过程中还发现并修正了一个方法论问题：仅关闭工具定义下发时，模型仍会依据系统提示词中的工具名发起调用，对照组被污染（实测仍有 4 题成功），最终改为"不下发 + 提示词裁剪 + 执行层拦截"三处联动才得到干净数据。

8.4 边界与安全测试

覆盖的边界包括：空输入与超长输入、日期越界、重复提交、并发抢位、越权访问、伪造图片地址、路径穿越、过期公告。安全测试确认：未登录访问返回 401，学生访问管理接口返回 403，学生查看他人资源返回 404，图片接口仅接受系统上传的相对路径。

九、设计总结

9.1 遇到的问题与解决方案

问题一：三库写入不一致。早期上传文档时，MySQL 写入成功但 Neo4j 未启动，导致页面上有文档、问答却查不到。解决方案是入库前做依赖预检，写入后任一环节失败即回滚已写数据，并把"文件已保存但入库失败"的文件清理掉。

问题二：PDF 解析与 Markdown 解析不一致。同一个条款，Markdown 解析出的正文不带编号，PDF 解析带"第 N 条"前缀，导致去重永远命中不了。解决方案是统一去重键：去掉条款编号与所有空白后再比较，同时用章节名做展示而不参与判重。

问题三：消融实验对照组被污染。只关闭工具定义下发时，模型仍按提示词里的工具名发起调用。解决方案是三处联动关闭，并在评测中只统计执行成功的调用。

问题四：前端高度写死导致布局错位。页面原本用 calc(100vh - 96px) 计算高度，加入顶部公告横幅后内容被裁切。解决方案是把页面高度改为 100%，由布局容器分配剩余空间。

问题五：预约接口把越界日期答成"有位置"。余量查询对越界日期返回"全部时段空闲"，工具直接透传会让模型给出错误结论。解决方案是在工具层前置校验日期范围，越界时返回明确的说明而不是空数据。

9.2 收获与不足

收获主要有三点：一是理解了 RAG 系统的可控性来自"检索范围约束 + 引用校验 + 拒答策略"，而不是换更大的模型；二是体会到交互设计对可信度的影响，同样一条回答，带来源卡片和草稿确认按钮时用户信任度明显更高；三是学会了用消融实验验证设计决策，而不是凭直觉判断某个功能"应该有用"。

不足也很明显：评测题集规模偏小（8 题），结论的统计意义有限；图谱部分目前只做到条款关系召回，尚未支持多跳推理；失物招领的图片识别、报修的图片上传仍是空白；系统尚未在真实高并发环境下压测，预约的并发结论来自本地线程级验证。
