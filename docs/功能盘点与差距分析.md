## 0. 一页结论

**判断：系统不"简单"，但明显"偏科"。**

- **问答内核不简单**：15 节点 Agent 图、向量 + 图谱双路召回、四态充分性判定、引用校验、13 个工具、写操作草稿确认、15 张表、216 个测试函数。这套深度在本科毕设中属于上游。
- **产品外围偏薄**：8 个页面里，报修 / 预约 / 失物是"学生能提交、本人能看、管理员能处理"的完整闭环，但**工单只有创建没有后续**；反馈只落库不消费；运营数据只在表里不在页面上；用户没有学院 / 年级 / 学历层次，无法区分本科与专科口径。
- **一句话**：技术纵深够写论文，产品闭环不够支撑"平台"两个字。答辩风险不在"系统太简单"，而在"讲不清谁在用、怎么运营、答错了怎么办"。

### 0.1 五维评分（10 分制，基于代码事实的主观判断）

| 维度 | 分数 | 主要依据 | 拉到 8 分需要补什么 |
|---|---|---|---|
| 技术深度 | 8.5 | 图引擎、双路召回、充分性判定、引用校验、并发控制 | 不需要大补 |
| 功能广度 | 6.0 | 问答 + 公告/报修/预约/失物 + 用户管理 | 通知、评价、办事目录 |
| 业务闭环 | 5.0 | 工单断链、反馈断链、运营断链 | 工单处理台、反馈工作台、看板 |
| 运营能力 | 3.0 | 无统计接口、无 bad case 池、无内容运营 | 看板 + 未命中池 |
| 体验完成度 | 6.5 | 问答主路径顺；会话管理 / 移动端 / 通知弱 | 会话管理、移动端、通知 |
| 工程规范 | 7.5 | 测试多、限流/降级/安全整改到位；无 CI / 监控 | CI + 指标告警 |

### 0.2 答辩最可能被问倒的三个问题

1. **"有多少人在用？大家最常问什么？答得准不准？"**——没有运营看板，只能现场跑离线评测脚本。
2. **"学生点了踩，然后呢？"**——反馈只写进 `feedback` 表，没有查看、归因、转语料修正的链路。
3. **"转人工之后谁处理？学生怎么知道进度？"**——工单只有 `POST /api/v1/tickets`，没有查询、没有流转、没有管理台。

## 3. 同类系统基准对照

### 3.1 参照系怎么选

"同类系统"不是单一产品，而是三类产品的并集：

1. **高校智能问答机器人**（教务处 / 学工处客服）：重知识准确性、拒答兜底、转人工、满意度。
2. **校园办事大厅**：重事项清单、办理流程、进度查询、通知、评价。
3. **企业级 RAG 知识库**：重知识治理、版本、评测、运营看板。

当前项目的题目是"校园服务智能问答系统"，**主线应按第 1 类 + 第 3 类评判**；第 2 类只在"服务平台"定位下才成为必备。这个定位判断直接决定下面的优先级。

## 4. 关键薄弱点

### 4.1 工单：有入口，没有出口（P0）

**现象**：`backend/app/api/v1/tickets.py` 只有一个 `POST /api/v1/tickets`；前端 `client.ts` 只有 `confirmTicket`；`tickets` 表的 `status`（open/processing/closed）没有任何流转接口。

**影响**：拒答后的"转人工"是问答系统最后的兜底，但学生拿不到工单号之后的信息，管理员也看不到待处理列表。答辩演示到"已提交：T-xxxx"就结束了，评委会追问"然后呢"。

**附带的表述风险**：`agents/tools.py` 的 `create_ticket` 在 query 命中"投诉/工单/转人工/故障"等关键词时**会直接落库**；未命中才返回草稿。README 写的是"一律二次确认后才落库"，两者不一致。需要统一为以下之一：
- 方案 A（推荐）：工具永远只出草稿，写入只走 `POST /tickets`；
- 方案 B：明确"高意图直接建单"，并在 README 与答辩口径中写清触发条件。

**建议**：新增 `GET /tickets`（我的 / 全部，管理员）、`GET /tickets/{id}`、`POST /tickets/{id}/transition`（accept / process / close，close 必填备注）；前端在"校园服务"加"我的工单" tab，管理员加处理台。直接复用报修的状态机与权限写法。

**成本估算**：1.5–2 人日。

### 4.2 反馈只进不出（P0）

**现象**：`feedback` 表 + `POST /api/v1/messages/{id}/feedback`，仅此。没有列表接口、没有聚合、没有归因字段、没有 bad case 池。

**影响**：
- 无法回答"答错了怎么办"，也就无法证明系统会随使用变好；
- 真实用户问题是最有价值的语料来源，现在全部沉睡在表里。

**建议**：管理端反馈列表（按 rating / 时间 / 关键词筛选）+ 归因标签（语料缺失 / 答案错误 / 引用错误 / 问题不清）+ 一键转入"待补语料"清单；看板展示满意度与低分问题 Top N。

**成本估算**：1 人日（与看板同批做）。

### 4.3 有数据，没运营（P0）

**现象**：`messages`、`feedback`、`tool_call_logs`、`conversations` 四张表都有数据，但没有 `/stats` 接口，也没有任何统计页面。全站搜索 `stats|dashboard|analytics` 无业务命中。

**影响**：答辩讲"系统效果"只能拿离线评测说事；上线后没有运营抓手，也无法发现"哪些问题总答不上来"。

**建议指标**（都能从现有表算出来，不需要新埋点）：
- 规模：日/周提问量、活跃用户数、会话数；
- 质量：拒答率、引用校验通过率、点赞率、低分问题 Top 20；
- 效率：P50 / P95 时延、工具调用成功率、缓存命中率；
- 内容：未命中问题 Top 20、零结果查询、热门问题 Top 20。

**成本估算**：1.5–2 人日（一个聚合接口 + 一个看板页）。

### 4.4 用户身份缺失，本科/专科口径会答错（P0）

**现象**：`users` 表只有 `username / nickname / role / status`；语料里同时存在 `03-学生学籍管理规定本科.md` 与 `04-学生学籍管理规定专科.md`。

**影响**：同一个问题（如"挂科几门会退学""重修怎么算"）对本科与专科的口径不同，系统无法区分用户身份，可能给出错误条款。这不是"功能少"，是"答案可能错"，在答辩现场比缺功能更致命。

**这是"已有数据没用上"的典型，性价比最高。**

**建议**：
- `users` 加 `education_level`（本科/专科）、`college`、`grade`；
- 注册时选择，管理员可补录；
- 检索时按学历做元数据过滤，或在提示词注入"当前用户为本科生，优先引用本科规定"；
- 答案中显式写明适用对象（"依据《本科学生学籍管理规定》第 X 条"）。

**成本估算**：0.5–1 人日。

### 4.5 知识库缺治理（P1）

**现象**：文档列表无关键词 / 标签 / 状态筛选；标签只在入库时自动打，没有管理页；条款写错只能删文档重传；上传是同步阻塞（OCR 单页约 8 秒）；表里已有 pending/processing/done/failed，但没有异步任务与状态轮询。

**影响**：语料一多就不可维护；答辩问"发现一条条款错了怎么改"，当前只能回答"删了重传"。

**建议**（可分两批）：
- 第一批：列表加 keyword / status / tag 筛选；文档详情支持单块编辑并只重建该块向量；
- 第二批：上传改异步任务 + 状态轮询 + 失败重试；标签管理页。

**成本估算**：2–3 人日。

### 4.6 状态变更无触达（P1）

**现象**：报修受理/完成、预约被管理员取消（`cancel_reason` 已落库）、失物审核通过/驳回，全部只在页面可见；无站内信、无消息中心。

**影响**：学生不主动回来看就永远不知道；"服务"体验在最后一步断掉。

**建议**：`notifications` 表 + 在三个模块的状态变更点发事件 + 顶部铃铛 + 未读计数。先做站内信，短信/微信模板消息不做（成本高、需要资质）。

**成本估算**：1.5–2 人日。

### 4.7 引用不能定位原文（P1）

**现象**：`SourceList.vue` 只展示 title / detail / snippet，不能点开原文位置；文档预览是新窗口打开整份 PDF。

**影响**："可溯源"打折扣；答辩只能展示片段，不能展示"这条引用在原文第几页第几条"。

**建议**：来源卡加"查看原文"→ 打开 preview 并带 `#page=` 或条款锚点；PDF 用 PyMuPDF 取页码，md/txt 用行号；前端滚动并高亮该条款。

**成本估算**：1 人日。

### 4.8 角色粒度粗（P1/P2）

**现象**：只有 admin / student；报修、预约、失物、公告、用户管理全部由 admin 处理。

**影响**：真实校园里后勤、图书馆、学工分权，当前无法表达。答辩若被问"谁能处理报修"，只能答"管理员"。

**建议**：暂不做复杂 RBAC。若要做，加一个 `staff_scope`（repair / reservation / lostfound / notice）即可；若不做，在设计文档里明确写"单管理员是课程规模的取舍"，不要留给评委猜。

**成本估算**：2–3 人日（P2，非必要）。

### 4.9 会话管理缺失（P1）

**现象**：`conversations` 只有 list / detail；无重命名、删除、归档、导出。

**影响**：历史页只能看不能整理；用户"删除我的会话"的隐私诉求无法满足。

**建议**：`PATCH /conversations/{id}`（标题）、`DELETE`（软删）、导出 Markdown。成本很低，体验提升明显。

**成本估算**：0.5 人日。

### 4.10 移动端适配薄弱（P1）

**现象**：全站仅 5 处 `@media`，侧栏、表格、问答输入区以桌面为主。

**影响**：校园场景手机为主；答辩若用手机演示会露怯。

**建议**：优先适配问答页与服务页：侧栏改抽屉、表格改卡片、触控目标 ≥44px。不做全站重写。

**成本估算**：1–2 人日。

## 5. 优先级建议

### 5.1 排序原则

1. **先补闭环，再加新模块**：已有数据 / 已有表能支撑的闭环优先，避免"再加一个半成品"。
2. **先修"答案可能错"，再修"体验不够好"**：身份字段影响正确性，优先级高于移动端。
3. **先做答辩能讲清楚的**：看板、反馈工作台、工单处理台都能直接回答评委的"然后呢"。
4. **范围控制**：本项目是"问答系统"，不是"办事大厅"；办事目录、服务评价在多模块并行前不立项。

### 5.2 P0（建议本周做，5–6 人日）

| 编号 | 建议 | 解决的短板 | 工作量（估算） | 答辩收益 | 依赖 |
|---|---|---|---|---|---|
| P0-1 | 工单闭环：列表 / 详情 / 状态流转 / 我的工单 / 管理台 | 转人工断链、进度不可查 | 1.5–2 人日 | 高 | 复用报修状态机 |
| P0-2 | 运营看板：提问量、活跃、拒答率、满意度、时延、未命中 Top | 无数据面、效果不可证 | 1.5–2 人日 | 高 | 数据已在库 |
| P0-3 | 反馈工作台：列表、归因标签、转待补语料 | 反馈黑洞、无法迭代 | 1 人日 | 高 | 与 P0-2 同批 |
| P0-4 | 用户身份：学历层次 / 学院 / 年级 + 检索过滤或提示词注入 | 本科/专科口径可能答错 | 0.5–1 人日 | 高 | 语料已区分本科/专科 |
| P1-5 | 会话管理：重命名 / 删除 / 导出 | 历史不可整理、隐私诉求 | 0.5 人日 | 中 | 无 |

> 这 5 项做完，产品完整度大致从 6 分拉到 8 分，且不需要新增外部依赖。

### 5.3 P1（下一批，5–7 人日）

| 编号 | 建议 | 解决的短板 | 工作量（估算） | 答辩收益 |
|---|---|---|---|---|
| P1-6 | 来源定位：来源卡 → 原文页码/条款高亮 | 引用不可定位 | 1 人日 | 中高 |
| P1-7 | 知识库治理：筛选 + 分块纠错（第一批） | 语料不可维护 | 1.5–2 人日 | 中 |
| P1-8 | 通知中心：站内信 + 未读计数 | 状态变更无触达 | 1.5–2 人日 | 中 |
| P1-9 | 热门问题 / 相关问题推荐 | 首问命中低 | 0.5–1 人日 | 中 |
| P1-10 | 移动端适配（问答页 + 服务页） | 手机体验差 | 1–2 人日 | 中 |

### 5.4 P2（有余力再做）

| 编号 | 建议 | 说明 | 工作量（估算） |
|---|---|---|---|
| P2-11 | 评测看板 | 把 `evaluate.py` 的结果可视化，展示回归基线 | 1.5 人日 |
| P2-12 | 图谱可视化 | 前端浏览"文档→章节→条款→主题"，答辩演示加分 | 1–1.5 人日 |
| P2-13 | 语音 / 图片提问 | 复用 OCR 链路，移动端价值高 | 2–3 人日 |
| P2-14 | 业务角色 `staff_scope` | 分权处理报修/预约/失物 | 2–3 人日 |
| P2-15 | CI + 指标告警 | GitHub Actions + 基础 metrics | 1 人日 |
| P2-16 | 办事目录 / 服务评价 | 仅当定位改为"校园服务门户"时立项 | 3–5 人日 |

### 5.5 两档增强包

**A. 最小答辩增强包（约 5–6 人日）**：P0-1 + P0-2 + P0-3 + P0-4 + P1-5。
产出：工单能查到进度、管理员能处理；看板能回答"用了多少、答得怎样"；反馈能归因并转语料；本科/专科口径不再混；历史能整理。

**B. 完整增强包（再 +5–7 人日）**：A + P1-6 + P1-7 + P1-9 + P1-10。
产出：引用能点回原文；知识库能筛选和纠错；首问有热门问题引导；手机能演示。

### 5.6 不建议现在做

| 不建议 | 原因 |
|---|---|
| 多租户 / 插件框架 / 工作流引擎 | 本科规模下抽象成本高于收益，评审也讲不清必要性 |
| Office 转 HTML/PDF 预览 | 转换服务部署成本高，415 + 提示"下载后查看"是合理边界 |
| 复杂 RBAC（部门/岗位/数据权限矩阵） | 没有真实多部门运营场景，做了也是空转 |
| 向量语义缓存 | 当前归一化精确匹配已够用，收益低、评测复杂 |
| 小程序 / 多端 | 除非答辩明确要求；先把 Web 端闭环做完整 |
| 全量前端重写 | 现有页面结构可用，重写不产生新能力 |
