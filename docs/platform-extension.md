# 校园服务平台扩展设计

> 面向毕业设计的模块划分与扩展机制说明。
> 本文描述"从问答系统扩展为校园服务平台"的整体范围、模块边界、实现方案与后续路线，
> 公告模块为本次落地内容，报修/预约给出可执行的扩展方案。

## 1. 定位调整

| | 调整前 | 调整后 |
| --- | --- | --- |
| 系统定位 | 校规问答（RAG + Agent） | 校园服务门户 |
| 问答的角色 | 全部功能 | **横切智能层**：任何模块的数据都能被问答调用 |
| 扩展方式 | 改核心代码 | 新增模块 → 注册路由与工具，核心不动 |

一句话：**问答不再是产品本身，而是贯穿各业务模块的入口**。
学生既可以点菜单看公告/报修，也可以直接问"今天哪里停水"，两条路径拿到的数据同源。

## 2. 模块划分

| 模块 | 状态 | 定位 | 数据来源 |
| --- | --- | --- | --- |
| 智能问答 | ✅ 已有 | 横切层：意图理解 → 检索/工具 → 证据约束生成 → 引用校验 | 校规知识库 + 各模块工具 |
| 校园公告 | 🔧 本次补全 | 时效性通知：停水停电、放假调课、考试安排、服务窗口调整 | `announcements` |
| 转人工工单 | ✅ 已有 | 兜底：投诉建议、需要人工跟进的问题 | `tickets` |
| 寝室报修 | ⬜ 预留 | 报修申请 + 处理流转 + 进度查询 | 复用 `tickets` 扩展 |
| 图书馆预约 | ⬜ 预留 | 座位/研讨间时段预约、违约记录 | 新增资源与预约表 |
| 失物招领 | ⬜ 预留 | 发布与检索 | 复用公告结构 |

## 3. 扩展机制：约定优于框架

不引入插件框架。本科规模下，插件系统带来的抽象成本高于收益。
取而代之的是**三条硬约定**，任何新模块照做即可接入：

```
1. backend/app/services/<key>.py     业务逻辑（MySQL 实现 + 内存实现各一份，便于测试）
2. backend/app/api/v1/<key>.py       build_router(...) 暴露 REST 接口
3. backend/app/agents/tools.py       在 TOOL_DEFINITIONS 注册工具，_dispatch 里接一行
```

三条约定带来的效果：

- **路由自动**：`main.py` 里 `app.include_router(build_<key>_router(...))` 一行；
- **问答可用**：工具注册后，`tool_agent` 会由 LLM 自主决定是否调用，不需要改图；
- **权限一致**：写操作统一 `if not user.is_admin: 403`，读操作登录即可。

已按此约定实现的模块：`documents`（知识库）、`tickets`（工单）、`notices`（公告）。
后续报修、预约照同一结构添加，不改动 `agents/` 下的任何代码。

## 4. 公告模块设计

### 4.1 为什么不是"再加一张表"

系统里原本已有 `announcements` 表和 `query_announcements` 工具，但**没有管理接口、没有页面**——
数据只能靠 SQL 手工插，问答能查到但学生看不到。本次补齐的是"可管理 + 可展示"，
而不是重建。

### 4.2 数据模型

在原表基础上补三个字段（`sql/migrations/002_notice_fields.sql`）：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `category` | VARCHAR(32) | 分类：`water` / `power` / `network` / `teaching` / `life` / `other` |
| `effective_at` | DATETIME | 生效时间，列表按此倒序 |
| `expires_at` | DATETIME | 失效时间，`NULL` 表示长期有效 |

为什么需要有效期：停水停电是**时段性**信息。"本周六 8:00-12:00 停水"发出去三天后还挂在列表上，
比不显示更糟。列表接口默认过滤 `expires_at < now()` 的记录，过期自动下架，不需要人工维护。

### 4.3 接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/notices` | 登录 | 列表，支持 `category` / `keyword` / `include_expired`，置顶优先、按生效时间倒序 |
| GET | `/api/v1/notices/{id}` | 登录 | 详情 |
| POST | `/api/v1/notices` | 管理员 | 发布（`status=published`）或存草稿 |
| PATCH | `/api/v1/notices/{id}` | 管理员 | 编辑 / 上下架 |
| DELETE | `/api/v1/notices/{id}` | 管理员 | 删除 |

### 4.4 与问答的集成

`query_announcements` 工具改为调用 `services/notices.search()`，与页面共用同一份过滤逻辑——
避免"页面看不到过期公告、问答却能答出来"的不一致。

工具的 `description` 补充触发词（停水、停电、放假、调课），提升 LLM 选择该工具的概率。

### 4.5 前端

- 新增 `/notices` 页面：卡片列表（置顶标记、分类标签、生效时间、"已结束"灰显）
- 管理员可见"发布公告"按钮，弹窗填写标题/分类/正文/有效期
- 侧边栏新增"校园公告"入口，与"智能问答"并列
- 问答页顶部展示最新一条未过期公告（可选，后续做）

## 5. 报修 / 预约扩展方案

### 5.1 寝室报修

复用 `tickets` 表，新增 `type` 字段区分 `complaint`（投诉）/ `repair`（报修），
并给报修补三个字段：`location`（楼栋房间）、`contact`、`handler_id`（处理人）。

状态机：

```
submitted → accepted → processing → done
                    ↘ rejected（附理由）
```

问答侧的扩展：新增工具 `query_repair_status(ticket_no)`，学生问"我的报修到哪一步了"可直接答。
写入仍走"二次确认"（见工单模块），避免 LLM 自主提交产生脏数据。

### 5.2 图书馆预约

需要两张新表：

- `resources`：可预约对象（座位区/研讨间），含容量、开放时段
- `bookings`：预约记录，含 `resource_id`、`user_id`、`slot_start`、`slot_end`、`status`

关键约束（用数据库唯一索引兜住，不靠应用层判断）：

```sql
UNIQUE KEY uk_slot (resource_id, slot_start, user_id)
```

防重复预约、防并发超卖。取消与违约另设 `status`，连续违约 N 次限制预约（规则可配置）。

### 5.3 不建议现在做的

- **不要为报修/预约先写空壳路由**：没有业务逻辑的接口只会增加维护面，评审时也讲不清；
- **不要引入工作流引擎**：三个状态用枚举 + 一张流转日志表足够；
- **不要给每个模块做独立前端工程**：单 SPA 加路由即可，拆开会让部署复杂一个量级。
