> 项目：`school-rules-rag-platform`（当前分支 `feat/admin-user-management`）
> 版本：v1.0
> 日期：2026-11-08
> 依据：代码实测（`backend/app`、`frontend/src`、`backend/tests`、`sql/migrations`）+ 上一份《功能盘点与差距分析》
> 用途：功能评估、排期、答辩取舍

## 0. 阅读说明

### 0.1 优先级定义

| 级别 | 定义 | 判断标准 | 建议处理 |
|---|---|---|---|
| P0 | 必须做 | 影响业务闭环、答案正确性或答辩硬伤；不做会被问倒 | 1–2 周内完成 |
| P1 | 应该做 | 明显影响体验、效率或可维护性；有明确使用场景 | 下一迭代（3–5 周） |
| P2 | 可以做 | 增强能力或工程保障；不做不影响主流程 | 有余力再做，或写入"后续计划" |

### 0.2 条目编号

- `N-xx`：新增功能（当前没有的接口、页面、能力）
- `M-xx`：现有功能修改（已有能力的行为、规则、文案、性能、体验调整）

### 0.3 与上一份报告的关系

《功能盘点与差距分析》回答"现在有什么、缺什么"；本文回答"具体怎么补、先补哪个、改哪里"。两份文档配合使用：前者用于判断，后者用于排期。

### 0.4 改进地图

| 模块 | 新增 P0/P1/P2 | 修改 P0/P1/P2 | 小计 |
|---|---|---|---|
| 智能问答与 Agent | 1 / 4 / 2 | 2 / 2 / 1 | 12 |
| 知识库与语料治理 | 0 / 2 / 3 | 0 / 3 / 2 | 10 |
| 校园服务 | 0 / 3 / 4 | 0 / 4 / 4 | 15 |
| 用户与权限 | 1 / 1 / 2 | 0 / 1 / 2 | 7 |
| 运营与数据 | 2 / 1 / 2 | 0 / 0 / 0 | 5 |
| 文档与交付口径 | 0 / 0 / 0 | 4 / 2 / 0 | 6 |
| 体验与工程 | 0 / 2 / 2 | 0 / 2 / 3 | 9 |
| **合计** | **4 / 13 / 15** | **7 / 15 / 10** | **64** |

> 64 条不是"都要做"。P0 共 11 条、约 9–10 人日；P1 按价值取前 10–12 条即可；P2 是 backlog，用于回答"后面还能做什么"。

### 0.5 执行摘要

- **最优先不是加新模块，而是补已有闭环**：工单有创建没处理、反馈有提交没消费、运营有数据没页面、用户有身份缺失。这四件事不做，加再多模块也只是多几个半成品。
- **P0 11 条约 9.5 人日**：工单闭环（2）、身份画像（1）、运营看板（2）、反馈与未命中工作台（2，含点踩原因）、工单口径与意图修正（1.5）、文档口径统一（1）。两周内可完成。
- **投入产出比最高的是文档口径统一**：不改代码，1 人日，直接消除答辩"数字对不上"的风险。
- **不建议现在做**：办事大厅、服务评价、复杂 RBAC、多端小程序。这些会让范围失控，且与"问答系统"的题目定位不一致。

## 1. 新增功能建议

### 1.1 智能问答与 Agent

| 编号 | 功能 | 用途 | 适用场景 | 优先级 | 工作量 |
|---|---|---|---|---|---|
| N-01 | 工单闭环与转人工工作台 | 让拒答后的转人工可查询、可处理、可关闭 | 学生投诉/建议/无法自助解决；管理员受理、处理、回访 | P0 | 2 |
| N-02 | 答案重新生成与详简控制 | 一次不满意可重答，支持"更简洁/更详细" | 答案过长、答非所问、需要给学生版与完整版 | P1 | 1 |
| N-03 | 澄清式追问 | 信息不足时先问清再答，而不是直接拒答 | 问题过短、多意图、缺时间/地点/对象 | P1 | 1 |
| N-04 | 热门问题与相关问题推荐 | 降低首问门槛，提升命中率 | 问答空状态、答案下方、公告详情页 | P1 | 1 |
| N-05 | 来源原文定位与条款高亮 | 让"可溯源"可验证 | 点来源→打开 PDF 对应页/条款高亮 | P1 | 1 |
| N-06 | 多模型降级与灰度开关 | DeepSeek 故障时自动切备用模型 | 公网部署、答辩现场网络异常 | P2 | 1.5 |
| N-07 | 语音输入与图片提问 | 移动端低门槛提问 | 拍通知/拍表格提问；需注意隐私与 OCR 质量 | P2 | 2.5 |

**重点说明**

**N-01 工单闭环与转人工工作台（P0）**
- 现状：`tickets` 表有 `status`（默认 `open`），但只有 `POST /api/v1/tickets`，没有查询与流转；前端只有确认提交按钮；表里也缺处理人、处理意见、关闭时间字段。
- 实施：补 `handler_id / handler_remark / closed_at` 三个字段（迁移 008）；新增 `GET /tickets`（学生=本人，管理员=全部，支持 status/关键词/分页）、`GET /tickets/{id}`、`POST /tickets/{id}/transition`（accept/process/close，close 必填备注）；前端在"校园服务"加"我的工单" tab，管理员加处理台。
- 验收：学生提交后能在列表看到状态变化；管理员能把单从 open 推到 closed；关闭后学生能看到处理意见；越权访问他人工单返回 404。

**N-03 澄清式追问（P1）**
- 现状：充分性判定只有"答/拒答/类比"三种出口，缺"先问一句"。
- 实施：在 `query_understand` 后加轻量判定——缺对象（哪个校区/哪个楼栋）、缺时间（哪一天）、多意图（同时问两件事）时返回澄清问题，不进入检索；澄清轮不写入拒答统计。
- 验收：输入"宿舍怎么办"能反问"你想问哪方面：熄灯/报修/调宿"；补全后能正常作答。

**N-04 热门问题与相关问题推荐（P1）**
- 数据来源：`messages` 按问题归一化聚合 Top N + 管理员人工精选；相关问题可按同一 `document_tags` 或同一意图推荐。
- 注意：不要在前端硬编码，避免与真实使用脱节。

### 1.2 知识库与语料治理

| 编号 | 功能 | 用途 | 适用场景 | 优先级 | 工作量 |
|---|---|---|---|---|---|
| N-08 | 标签管理与按标签检索 | 让已有 `document_tags` 真正可用 | 文档列表按主题筛选；问答按主题缩小检索范围 | P1 | 1 |
| N-09 | 分块纠错与单块重建 | 条款写错不用删整篇 | OCR 错字、条款缺失、口径更新 | P1 | 1.5 |
| N-10 | 知识版本与生效期 | 支持新旧制度并存与按日期检索 | 学籍规定换版、奖助金额调整 | P2 | 2 |
| N-11 | 批量导入与目录同步 | 一次性导入整本手册或整个目录 | 开学前更新制度 | P2 | 2 |
| N-12 | 语料质量体检 | 自动发现断条、重复、口径冲突 | 入库前检查、答辩前自查 | P2 | 1.5 |

**重点说明**

**N-09 分块纠错与单块重建（P1）**
- 现状：文档只能整篇删除重传；`chunks` 表已有 `qdrant_point_id`，具备单块重建条件。
- 实施：文档详情页的每个分块加"编辑"；保存后更新 `chunks.content`、重建该块向量、更新 Neo4j 对应条款节点，并清理相关缓存。
- 验收：改一个错字后，用包含该错字的旧问法检索不再命中旧文本，新问法能命中新文本；其余分块向量不变。

**N-12 语料质量体检（P2）**
- 检查项：条款号断号（如缺第十八至二十四条）、同制度多版本、金额/期限口径冲突、重复条款、超长块。
- 输出：一份可下载的体检报告；不自动修改语料，避免误伤。

**重点说明**

**N-13 通知中心（P1）**
- 现状：状态变更只在页面可见；预约取消原因 `cancel_reason` 已落库，但学生不主动回来看就不知道。
- 实施：新增 `notifications` 表（user_id、type、title、body、link、read_at）；在报修 `process/complete/close`、预约 `cancel`、失物 `approve/reject/resolve` 等服务函数内发事件；前端顶部铃铛 + 未读计数 + 消息列表。
- 注意：先做站内信，不做短信/微信模板消息（需要资质与成本）；通知失败不能影响主业务事务。

**N-14 报修图片、优先级与 SLA（P1）**
- 现状：`repair_requests` 无图片字段；所有报修同一优先级；无超时提醒。
- 实施：复用失物招领的上传链路（白名单/大小/数量）；加 `priority`（普通/紧急）与 `sla_hours`；列表按优先级与超时排序；超时在管理台标红。
- 验收：紧急报修在管理员列表置顶；超过 SLA 未处理的单有醒目标记；图片只能本人与管理员查看。

- 现状：`users` 只有 `username/nickname/role/status`；语料同时存在 `03-学生学籍管理规定本科.md` 与 `04-学生学籍管理规定专科.md`。

- 迁移策略：存量用户默认"未设置"，首次登录引导补全；未设置时不硬猜，回答中说明"本科与专科口径不同，请确认身份"。
- 验收：本科生问"挂科几门会退学"只引用本科规定；专科生只引用专科规定；未设置用户会收到身份确认提示。

**重点说明**

**N-24 运营看板（P0）**
- 数据全部来自现有表，不需要新埋点：
  - 规模：日/周提问量、活跃用户、会话数（`conversations`、`messages`）；
  - 质量：拒答率、引用校验通过率、点赞率、低分问题 Top 20（`messages`、`feedback`）；
  - 效率：P50/P95 时延、工具调用成功率、缓存命中率（`messages.latency_ms`、`tool_call_logs`）；
  - 内容：未命中问题 Top 20、零结果查询、热门问题 Top 20。
- 注意：MySQL 5.5 不支持窗口函数，聚合用 `GROUP BY` + 子查询。
- 验收：答辩时能在 10 秒内回答"上周多少问题、拒答率多少、最常问什么、最答不上来什么"。

**N-25 反馈与未命中工作台（P0）**
- 功能：反馈列表（按 rating/时间/关键词筛选）、归因标签（语料缺失/答案错误/引用错误/问题不清）、一键转入"待补语料"清单；未命中问题按归一化聚合，支持标记"已补/忽略"。
- 闭环：待补语料 → 管理员补文档或 FAQ → 状态改为"已处理" → 下周看板对比。
- 验收：一条点踩能走到"已归因→已补语料→已复核"三个状态，且全程有操作人和时间。

## 2. 现有功能修改建议

### 2.1 智能问答与 Agent

| 编号 | 修改项 | 现状与问题 | 修改原因 | 预期效果 | 优先级 | 工作量 |
|---|---|---|---|---|---|---|
| M-01 | 工单写入统一为"草稿 + 确认" | `create_ticket` 在 query 命中"投诉/工单/转人工/故障/坏了/维修"等词时直接写库；未命中才返回草稿。README 写"一律二次确认后才落库" | 写操作不可控，且文档与代码不一致；答辩容易被抓 | 所有工单写入都经用户点击确认；工具只出草稿；口径统一 | P0 | 0.5 |
| M-02 | 收敛工具意图边界与关键词 | `create_ticket` 描述含"设备报修"，关键词含"坏了/维修/故障/人工/建议"；与 `create_repair_draft` 职责重叠；"人工"会匹配"人工智能" | 寝室报修可能被建成投诉工单；泛词导致误触发 | 报修走报修草稿、投诉走工单；误触发显著下降 | P0 | 1 |
| M-03 | 点赞点踩补充原因 | 后端 `FeedbackRequest` 支持 `comment`，前端只传 `rating`，`comment` 从未被使用 | 低分无法归因，反馈工作台没有分析材料 | 点踩时弹出原因选择/补充；反馈可统计 | P0 | 0.5 |
| M-04 | 展示引用校验状态 | `grounding_status`（verified/unverified/skipped）已在 `types.ts`，界面不展示 | 用户不知道引用是否核对过，"可溯源"缺最后一环 | 答案底部显示"引用已核对/未通过/工具直答" | P1 | 0.5 |
| M-05 | 拒答话术分场景 | 所有无证据场景统一用 `NO_EVIDENCE_ANSWER` | 无证据、超出范围、敏感问题的下一步不同 | 拒答更可解释；该转人工的转人工，该换问法的给建议 | P1 | 0.5 |

**重点说明**

**M-01 + M-02 建议同批做（P0，1.5 人日）**
- M-01：删除 `create_ticket` 里的直接落库分支，统一返回 `requires_confirmation=true` 的草稿；写入只保留 `POST /api/v1/tickets`。同步修改 README 与系统提示词第 10 条，明确"所有 create_* 都是草稿"。
- M-02：
  - 从 `create_ticket` 的 description 中删除"设备报修"，改为"投诉、举报、服务建议、需要人工跟进的非报修事项"；
  - `TICKET_INTENT_KEYWORDS` 移除"坏了/维修/故障/人工/建议"等泛词，保留"投诉/举报/转人工/工单/反馈"；"人工"改为"转人工"或正则 `(?<!智能)人工`；
  - 在 `create_repair_draft` 的 description 中补"寝室水电/网络/家具/门窗故障"，并在系统提示词强调"报修不要用 create_ticket"。
- 验收用例：
  - "宿舍灯坏了" → `create_repair_draft`，不出现工单；
  - "我要投诉宿管" → `create_ticket` 草稿，确认后才落库；
  - "什么是人工智能" → 不触发 `create_ticket`；
  - "我的报修到哪了" → `query_repair_status`，不建单。

### 2.2 知识库与语料治理

| 编号 | 修改项 | 现状与问题 | 修改原因 | 预期效果 | 优先级 | 工作量 |
|---|---|---|---|---|---|---|
| M-06 | 文档列表加筛选与分页 | `list_documents` 无参数；前端无搜索/标签/状态筛选 | 文档一多就不可维护 | 按关键词/状态/标签筛选，分页加载 | P1 | 1 |
| M-07 | 文档详情补标签、来源、上传者 | `DocumentItem` 只有基础字段；`document_tags` 有数据但无接口暴露 | 标签白打，来源不可追溯 | 详情能看到主题标签与 `_sources.json` 来源 | P1 | 0.5 |
| M-08 | 上传异步化与状态轮询 | 上传同步执行，`status` 固定写 `done`；大 PDF/OCR 会阻塞请求 | 请求超时、用户不知道进度 | 上传即返回任务号，状态可查、失败可重试 | P1 | 1.5 |
| M-09 | 删除清理与标签规则 | 删除文档清三库；失物图片在驳回/下架/删除时不清理；标签规则写死在代码里 | 孤立文件占磁盘、有隐私风险；规则不可调 | 资源不泄漏；标签规则可配置 | P2 | 1 |
| M-10 | 切块参数按文档类型可配 | 固定 600 字 + 80 重叠 + 1200 上限 | 制度、指南、FAQ 的结构差异大 | 不同文档类型用不同切块策略，召回更稳 | P2 | 0.5 |

**重点说明**

**M-08 上传异步化（P1）**
- 现有 `documents.status` 已有 pending/processing/done/failed，但从未使用；改造不需要新表。
- 实施：上传接口先落 `pending` 记录并返回 `document_id`，后台任务解析/切块/写三库，完成后置 `done`，失败置 `failed` 并存错误摘要；前端列表轮询或 SSE 推送状态。
- 验收：上传 20MB 扫描件时接口 2 秒内返回；列表能看到 processing → done；失败可重试且不产生半成品。

**M-14 违约限制（P1）**
- 规则建议：连续 2 次 `no_show` → 禁止预约 7 天；违约记录保留一学期；管理员可手动解除。
- 注意：不要用"累计违约"一刀切，避免一次误操作长期禁约；规则参数放 `Settings`，便于答辩时说明可配置。
- 验收：连续两次 no_show 后第 3 次预约返回 429 并提示解禁时间；`fulfilled` 或正常取消会重置连续计数。

**M-15 流转备注（P1）**
- 现状：`process/complete` 可无备注，学生只看到状态变了，不知道为什么。
- 建议：`process/complete` 也要求至少 5 字处理说明；前端在流转弹窗里预置常用语（已联系后勤/已更换配件/需另约时间）。

### 4.1 P0 整体验收

## 5. 不建议现在做

| 不建议 | 原因 |
|---|---|
| 多租户 / 插件框架 / 工作流引擎 | 本科规模下抽象成本高于收益，评审也讲不清必要性 |
| Office 转 HTML/PDF 预览 | 转换服务部署成本高；415 + "下载后查看"是合理边界 |
| 复杂 RBAC（部门/岗位/数据权限矩阵） | 没有真实多部门运营场景；`staff_scope` 足够 |
| 向量语义缓存 | 当前归一化精确匹配已够用，收益低、评测复杂 |
| 小程序 / 多端 | 先把 Web 端闭环做完整；除非答辩明确要求 |
| 全量前端重写 | 现有页面结构可用，重写不产生新能力 |
| 自研 Embedding / 微调大模型 | 成本高、周期长，超出本科毕设范围；BGE + DeepSeek 已够 |
| 知识图谱自动本体学习 | 演示价值有限，工程复杂度高 |

## 6. 风险与注意事项

| 风险 | 影响 | 应对 |
|---|---|---|
| 身份字段迁移影响存量用户 | 老用户没有学历，可能被错误过滤 | 默认"未设置"，不硬猜；未设置时回答中说明口径差异 |
| 工单状态机与报修状态机混用 | 两个模块职责混乱 | 保持两张表、两套状态；只复用写法，不复用表 |
| 看板 SQL 在 MySQL 5.5 不兼容 | 页面报错 | 避免窗口函数，用 GROUP BY + 子查询；本地 5.5 实测 |
| 通知侵入业务事务 | 通知失败导致报修/预约回滚 | 通知在事务提交后发；失败只记日志，不影响主流程 |
| 异步上传任务丢失 | 文档卡在 processing | 启动时扫描超时任务置 failed；提供重试 |
| 文档口径改了但 PPT 没改 | 答辩仍不一致 | 口径对照表纳入答辩检查清单 |
| 移动端适配范围失控 | 拖慢 P1 进度 | 只做问答页与服务页，其他页面保持桌面可用 |
